# Operational Canary Threat Model (Spec 92)

Threat cases from Spec 92 Sec 25, scoped to the decision-to-outcome
backend added in `docs/specs/92_governed_decision_to_outcome_backend_rc.md`.
Each entry names the actual mitigation and the test that exercises it —
this is not a design intention document, it describes what the code
currently does.

| # | Threat | Mitigation | Evidence |
| --- | --- | --- | --- |
| 1 | **Opportunity tampering** — a `MarginOpportunity` row is altered after a recommendation was built from it | `before_update`/`before_delete` ORM listeners reject any change to `margin_opportunities` unconditionally; `GovernedRecommendation.source_content_hash` freezes the opportunity's `content_hash` at recommendation-creation time | `erpguard/db/model_packages/opportunity.py::reject_margin_opportunity_mutation`; evidence-bundle sealing re-verifies `margin_opportunity.content_hash` still matches (`test_phase20_2_decision_outcome_evidence.py::test_altered_stored_hash_fails_verification_and_read`) |
| 2 | **Recommendation substitution** — swap which recommendation an approval/action-draft/run actually authorizes | `Approval.scope` is bound to `recommendation:{id}:approve:{content_hash}` — an approval scoped to one recommendation's exact content cannot be replayed against a different (or edited) one; `GovernedActionDraft.content_hash` embeds `recommendation_content_hash` | `erpguard/application/recommendations/service.py::approve` (`approval_scope_mismatch`); `test_phase16_7_recommendation_to_action.py::test_changed_source_hash_invalidates_conversion` |
| 3 | **Approval replay** — reuse a single-use `Approval` across two runs/recommendations/policies | `Approval.used_at`/`used_by_run_id` set atomically on first use; every consumer (`RecommendationService.approve`, `PermitService.approve`, `CanaryRouterService.approve_policy`, `OutcomeService.approve_plan`) checks `used_at is not None` first | `erpguard/db/model_packages/execution.py::reject_used_approval_update`; `test_phase15_execution_permit_runtime.py` approval-reuse cases |
| 4 | **Action-template injection** — smuggle an arbitrary capability/connector through an action draft | Templates are a fixed, code-defined dict (`erpguard/domain/recommendations/templates.py::ACTION_TEMPLATES`) — `selected_action_template` is validated against it at recommendation *creation*, and `capability`/`connector_id` on the draft are copied from the template, never from request input | `RecommendationService.create` (`unknown_action_template`); `test_phase16_7_recommendation_to_action.py` |
| 5 | **Price manipulation** — propose a price/margin the recommendation's own evidence doesn't support | Domain-level `validate_pricing_scenario` enforces a minimum-margin floor per line against `cost_reference` *before* an action draft is built; the connector's postcondition independently re-derives the same margin from the *executed* order's actual price and blocks (`postcondition_failed:margin_floor_violated`) if it drifted between planning and execution | `erpguard/domain/recommendations/validation.py`; `erpguard/connectors/odoo/plugin.py::_verify_pricing_scenario_draft`; `test_phase16_7_pricing_scenario_draft.py::test_margin_floor_violation_blocks` |
| 6 | **Cross-tenant object references** — read or act on another tenant's recommendation/policy/bundle | Every query in every service filters by `tenant_id` explicitly (`filter_by(tenant_id=..., id=...)`); there is no lookup-by-id-alone path anywhere in Workstreams A/B/D | `test_phase19_2_operational_canary_router.py::test_another_tenant_cannot_inspect_policy`; `test_phase20_2_decision_outcome_evidence.py::test_another_tenant_cannot_read_bundle` |
| 7 | **Canary bucket manipulation** — bias routing without going through a real `CanaryPolicy` percentage | `bucket = sha256(tenant_id, canary_policy_id, process_key, business_object_key) mod 10000` is a pure function of immutable inputs (`erpguard/domain/canary/routing.py`) — no caller-suppliable seed, no seedable RNG state, nothing to bias short of the actual approved `percentage_basis_points` | `test_phase19_2_operational_canary_router.py::test_bucket_is_deterministic_for_same_inputs`, `::test_select_lane_boundary_percentages` |
| 8 | **Explicit canary bypass** — an operator plans a run against the `canary`-status package directly, skipping the router | `PermitService.plan()`'s eligibility check (`_EXECUTABLE_STATUSES`) allows `canary`-status packages to be named explicitly by `skill_package_id` — Sec 9.5 point 2 restricts this path to admin/staging test mode at the API-authorization layer (`require_role`), not at the connector; routing-context planning is the only path available to `operator` role | `apps/api/routes/public_v1/executions.py` (`require_role`); `erpguard/domain/execution/permit_service.py::_EXECUTABLE_STATUSES` |
| 9 | **Concurrent double promotion / double policy activation** | `SkillDeploymentService.promote_to_active` and `CanaryRouterService.activate` both query for an existing `active` row for the same `(tenant_id, process_key)` inside the same transaction before flipping status; SQLite tests assert the application-level check, Sec 13's partial unique index is the PostgreSQL-level backstop for the same invariant | `test_phase19_2_operational_canary_router.py::test_two_active_policies_for_same_process_rejected`; `test_phase19_skill_deployment_lifecycle.py` |
| 10 | **Stale active-package resolution** — route to a package that was just rolled back or deprecated | `get_active()` is a live query (`status == "active"`), never cached; `rollback()` flips the old package to `rolled_back` in the same transaction that (optionally) restores the prior `deprecated` package to `active` — there is no window where two rows both read `active` | `erpguard/domain/deployment/service.py::rollback`; `test_phase19_skill_deployment_lifecycle.py::test_promote_to_active_supersedes_prior_active_and_rollback_restores_it` |
| 11 | **Evidence-chain tampering** — alter a resource reference inside a sealed `DecisionOutcomeEvidenceBundle` | The bundle row itself is fully immutable once `sealed` (ORM listener rejects *any* update); `chain_hash` folds every reference in order, so a raw-SQL edit to `manifest_json` (bypassing the ORM) is caught on next `GET` (`_revalidate_stored_hashes`, recomputes `manifest_hash`/`chain_hash` from the stored manifest) and on `verify()` (re-fetches every referenced resource's *current* hash) | `erpguard/db/model_packages/decision_outcome_evidence.py::reject_sealed_bundle_update`; `test_phase20_2_decision_outcome_evidence.py::test_altered_stored_hash_fails_verification_and_read`, `::test_sealed_bundle_is_immutable` |
| 12 | **Outcome fabrication** — claim a realized value / causal effect the evidence doesn't support | `RealizedOutcomeReport` classification and `realized_value` are computed only from a comparison that passed every gate (metric version, currency, coverage, unblocked baseline/follow-up); `interpretation.py` hard-codes `"observed_change_is_not_a_causal_claim"` into every report and the codebase contains no `proved`/`caused`/`guaranteed` string on this path; missing implementation cost leaves `net realized value` undefined rather than assumed | `erpguard/domain/outcomes/interpretation.py`; `test_phase20_1_realized_outcomes.py::test_metric_version_mismatch_blocks` etc. |
| 13 | **Secret leakage** — a credential, API key, or vault reference enters an evidence bundle, run payload, or dashboard | No gathered resource in `DecisionOutcomeEvidenceService._gather` ever references `UnifiedConnection.secret_ref` or `EncryptedSecret`; `contains_secret_like_field` additionally key-name-scans the manifest/export payload (`secret`, `credential`, `password`, `api_key`, `token`, `private_key`, `access_key`) and `seal()`/`export()` refuse to proceed if it matches anything | `erpguard/domain/evidence/decision_outcome_bundle.py::contains_secret_like_field`; `test_phase20_2_decision_outcome_evidence.py::test_secret_like_field_rejected_from_export`, `::test_no_secret_present_in_sealed_manifest`; `test_phase16_7_pricing_scenario_draft.py::test_draft_created_retry_idempotent_and_no_credential_in_evidence` |
| 14 | **Idempotency-key collision** — two different operations reuse the same idempotency key | `PermitService.plan()` looks up any prior `ExecutionRun` with the same `(tenant_id, idempotency_key)`; if the `operation_hash` differs it raises `IdempotencyConflict` rather than silently returning the wrong run, and only an exact-hash match short-circuits to the existing row | `erpguard/domain/execution/permit_service.py::plan` (`IdempotencyConflict`); `test_phase15_execution_permit_runtime.py` |

## Live verification note

No residual risk remains open from this delivery's original list (canary
dashboard `estimated_opportunity_value` and net ROI with implementation
cost are both now implemented — see
`docs/specs/92_governed_decision_to_outcome_backend_rc.md`).

- **The pricing-scenario write was verified live, including genuinely
  canary-routed** (Sec 19/20) — two real Odoo skill packages sharing one
  process_key, an activated `CanaryPolicy`, and a `routing_context`-planned
  run that `CanaryRouterService` actually routed to the canary package
  (confirmed on the persisted `ExecutionRun.deployment_lane` and by
  re-running the deterministic routing math independently before spending
  the real write). Two draft `sale.order` rows were created against the
  real staging instance (one direct-to-stable, one canary-routed), each
  independently re-read and retry-proven idempotent. See
  `docs/demo/backend_rc_live_pricing_scenario_evidence.json`.
